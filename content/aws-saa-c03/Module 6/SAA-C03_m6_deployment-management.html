6.2 — Infrastructure as Code with AWS CloudFormation

Khái niệm: Mô tả toàn bộ hạ tầng trong 1 template YAML/JSON, AWS tự tạo/sửa/xóa đúng thứ tự phụ thuộc. Giống đưa bản vẽ kỹ thuật cho nhà thầu thay vì tự xây tay từng viên gạch.

  • Stack = 1 lần deploy = tập resource quản lý cùng nhau
  • Change Set = xem trước thay đổi trước khi apply
  • Nested Stack = stack cha gọi nhiều stack con
  • Drift Detection = phát hiện resource bị sửa tay ngoài luồng

Pattern nâng cao: Dùng validate-template + cfn-lint trước khi commit. Case thực tế: startup SaaS B2B dùng 1 template với Parameters (EnvType) để CI/CD tự deploy dev/staging/prod giống hệt nhau, tránh lỗi "chạy được ở staging nhưng lỗi ở prod".

Vị trí kiến trúc: Không phải trạm sản xuất — là bản vẽ kỹ thuật + đội thi công dựng toàn bộ nhà máy, đứng trên toàn bộ bản đồ nền, ngoài luồng xử lý request khách hàng.

5 câu hỏi ôn tập
  1. Xem trước thay đổi trước khi apply stack production dùng gì? → Change Set.
  2. Phát hiện ai đó sửa tay Security Group ngoài CFN? → detect-stack-drift.
  3. Vì sao startup 3 môi trường nên dùng CFN? → Đồng nhất dev/staging/prod, giảm lỗi.
  4. Dùng lại VpcId ở stack khác không hardcode? → Outputs+Export / Fn::ImportValue.
  5. CFN khớp trạm nào? → Không khớp trạm nào — là bản vẽ + đội thi công.
aws cloudformation create-stack \
  --stack-name my-vpc-stack \
  --template-body file://vpc.yaml \
  --capabilities CAPABILITY_NAMED_IAM

aws cloudformation create-change-set \
  --stack-name my-vpc-stack \
  --change-set-name preview-01 \
  --template-body file://vpc-v2.yaml

aws cloudformation execute-change-set \
  --change-set-name preview-01 --stack-name my-vpc-stack

aws cloudformation detect-stack-drift --stack-name my-vpc-stack

6.5 — Platform as a Service with AWS Elastic Beanstalk

Khái niệm: PaaS — upload code, EB tự tạo EC2+ASG+ELB+SG+CloudWatch bên dưới. Như thuê xưởng đóng gói sẵn thay vì tự xây/tuyển thợ.

  • Web server environment: nhận HTTP qua ELB
  • Worker environment: xử lý job nền, tự tạo SQS

Pattern nâng cao: Deployment policy Immutable cho zero-downtime tuyệt đối. Case: team 3 người build MVP TMĐT dùng .ebextensions cài extension, eb deploy nhiều lần/ngày mà không quản chi tiết ASG/ALB.

Vị trí kiến trúc: Không phải trạm mới — combo đóng gói sẵn của Sảnh phân luồng (ALB) + Xưởng lắp ráp (ASG/EC2).

5 câu hỏi ôn tập
  1. Zero-downtime tuyệt đối chọn policy nào? → Immutable.
  2. Worker environment tự tạo thêm resource gì? → SQS queue.
  3. Vì sao startup nhỏ chọn EB? → Không đủ người vận hành hạ tầng.
  4. Cài thêm package OS lúc provision sửa ở đâu? → .ebextensions/*.config.
  5. EB khớp đâu trong nhà máy? → Combo ALB + ASG/EC2 đóng gói sẵn.
eb init my-app --platform python-3.9 --region ap-southeast-1
eb create my-env --instance-type t3.micro --elb-type application
eb deploy
eb status
eb logs
eb terminate my-env

6.7 — SSM Parameter Store

Khái niệm: Kho key-value cho config/secret, versioning, mã hóa KMS (SecureString). Như sổ tay dùng chung có khóa thay vì dán số điện thoại lên tường.

  • Standard: miễn phí, 4KB
  • Advanced: trả phí, 8KB, throughput cao hơn

Pattern nâng cao: Path hierarchy /{env}/{service}/{key} + IAM theo path prefix. Case: microservice trên EKS đọc config runtime lúc khởi động thay vì bake vào Docker image.

Vị trí kiến trúc: Lớp phủ cùng nhóm KMS — sổ tay cấu hình dùng chung cho Xưởng lắp ráp và Thợ thời vụ.

5 câu hỏi ôn tập
  1. Lưu password mã hóa dùng type nào? → SecureString.
  2. Vì sao service EKS đọc config qua Parameter Store? → Đổi config không cần build lại image.
  3. Standard tier giới hạn kích thước? → 4KB.
  4. Giới hạn team chỉ đọc /staging/*? → IAM policy theo path prefix.
  5. Khớp đâu trong nhà máy? → Cạnh KMS, lớp phủ an ninh.
aws ssm put-parameter --name "/prod/db/password" \
  --value "S3cret!" --type SecureString --key-id alias/my-key

aws ssm get-parameter --name "/prod/db/password" --with-decryption

aws ssm get-parameters-by-path --path "/prod/db/" --recursive

6.8 — AWS Config

Khái niệm: Ghi lại trạng thái cấu hình resource, so sánh với rule để phát hiện non-compliant. Như nhân viên kiểm định đi vòng quanh nhà máy ghi nhật ký. Khác CloudTrail: Config ghi trạng thái/lịch sử, CloudTrail ghi ai gọi API gì.

Pattern nâng cao: Auto Remediation qua SSM Automation. Case: ngân hàng dùng Config Aggregator gộp compliance toàn Organization, xuất báo cáo cho audit.

Vị trí kiến trúc: Lớp phủ an ninh, nhân viên kiểm định cấu hình (khác GuardDuty — đội tuần tra kẻ lạ).

5 câu hỏi ôn tập
  1. Config khác CloudTrail điểm nào? → Trạng thái cấu hình vs hành động API.
  2. Tự sửa khi phát hiện S3 public? → Auto Remediation qua SSM Automation.
  3. Gộp compliance nhiều account? → Config Aggregator.
  4. Managed rule không đủ? → Custom Config Rule bằng Lambda.
  5. Khớp đâu trong nhà máy? → Lớp phủ an ninh, nhân viên kiểm định.
aws configservice put-configuration-recorder \
  --configuration-recorder name=default,roleARN=arn:...role/config-role
aws configservice start-configuration-recorder --configuration-recorder-name default
aws configservice put-config-rule --config-rule file://s3-public-read-prohibited.json
aws configservice get-compliance-details-by-config-rule \
  --config-rule-name s3-bucket-public-read-prohibited

6.10 — AWS Secrets Manager

Khái niệm: Lưu secret mã hóa KMS, có auto-rotation tích hợp RDS/Aurora/Redshift/DocumentDB. Như hộp khóa số tự đổi mã mỗi tháng.

Pattern nâng cao: Cross-region replica cho DR. Case: sàn giao dịch tài chính đổi password DB mỗi 30 ngày tự động không downtime.

Vị trí kiến trúc: Cùng khu Parameter Store, sổ tay bí mật có tự đổi khóa định kỳ.

5 câu hỏi ôn tập
  1. Khác biệt lớn nhất so với Parameter Store? → Auto-rotation tích hợp RDS/Aurora.
  2. Đổi password mỗi 30 ngày không downtime? → Secrets Manager + Lambda rotation.
  3. Secret sẵn sàng ở region DR? → Cross-region replication.
  4. Kích thước tối đa? → 64KB.
  5. Khớp đâu trong nhà máy? → Cùng khu Parameter Store, lớp phủ an ninh.
aws secretsmanager create-secret --name prod/db/password \
  --secret-string '{"username":"admin","password":"S3cret!"}'
aws secretsmanager get-secret-value --secret-id prod/db/password
aws secretsmanager rotate-secret --secret-id prod/db/password \
  --rotation-lambda-arn arn:...function:rotate-rds \
  --rotation-rules AutomaticallyAfterDays=30

6.11 — AWS Resource Access Manager

Khái niệm: Chia sẻ resource (subnet, TGW, license) giữa nhiều account mà không cần duplicate. Như xây 1 con đường chung thay vì mỗi phòng ban tự xây riêng.

Pattern nâng cao: Share Transit Gateway trung tâm cho toàn Organization. Case: tập đoàn nhiều BU dùng chung 1 subnet đặt Active Directory thay vì mỗi BU tự dựng.

Vị trí kiến trúc: Trạm mới — "hợp đồng thuê chung" hạ tầng giữa các account, cạnh AWS Organizations.

5 câu hỏi ôn tập
  1. RAM khác VPC Peering ở đâu? → Chia sẻ resource cụ thể, không chỉ network.
  2. Trong cùng Organization cần accept thủ công? → Không, tự động nếu đã bật sharing.
  3. Tập đoàn nhiều BU dùng chung subnet AD? → RAM share subnet.
  4. Share TGW cho account con cần gì trước? → Bật sharing với Organizations.
  5. Khớp đâu trong nhà máy? → Trạm mới, hợp đồng thuê chung, cạnh Organizations.
aws ram create-resource-share --name shared-subnet \
  --resource-arns arn:aws:ec2:...:subnet/subnet-abc123 \
  --principals 222222222222

aws ram enable-sharing-with-aws-organization
aws ram get-resource-shares --resource-owner SELF

6.13 — RPO, RTO, and DR Strategies

RPO = dữ liệu tối đa chấp nhận mất. RTO = thời gian tối đa chấp nhận downtime. Như "save file lần cuối lúc nào" (RPO) và "mất bao lâu mở lại máy" (RTO).

Pattern nâng cao: Luôn chọn chiến lược rẻ nhất đáp ứng đủ RTO/RPO đề bài cho. Case: công ty bảo hiểm cần RPO 5 phút chọn Pilot Light thay vì Warm Standby/Active-Active đắt hơn.

Vị trí kiến trúc: Không phải 1 trạm — bản kế hoạch dự phòng toàn nhà máy; Route 53 chuyển hướng khách sang nhà máy phụ khi cần.

5 câu hỏi ôn tập
  1. RPO đo gì, RTO đo gì? → Dữ liệu mất tối đa vs thời gian downtime tối đa.
  2. RPO 5 phút, ngân sách hạn chế? → Pilot Light.
  3. Chiến lược RPO/RTO ~0 nhưng đắt nhất? → Multi-site Active/Active.
  4. Cơ chế tự chuyển traffic sang DR? → Route 53 Failover routing.
  5. Nguyên tắc chọn chiến lược khi đề cho RTO/RPO? → Rẻ nhất vẫn đáp ứng đủ.

Secrets Manager có auto-rotation tích hợp RDS/Aurora, Parameter Store thì không.
4. AWS Config khác CloudTrail ở điểm nào?
Config ghi trạng thái cấu hình + lịch sử thay đổi; CloudTrail ghi ai gọi API gì.
5. RAM dùng để làm gì?
Chia sẻ resource (subnet, TGW, license) giữa nhiều account mà không cần duplicate.
6. Công ty bảo hiểm cần RPO 5 phút, ngân sách hạn chế — chọn chiến lược DR nào?
Pilot Light — DB sync liên tục (RPO thấp), compute tắt sẵn (RTO chấp nhận cao hơn).
7. Nested stack yêu cầu điều gì đặc biệt về template con?
Phải nằm trên S3 (TemplateURL), không dùng file:// local trực tiếp.

Cheat Sheet — Deployment and Management

CloudFormation vs Beanstalk

CFN = IaC toàn bộ resource. Beanstalk = PaaS chỉ web app, tự dựng ASG/ELB bên dưới. Change Set = xem trước thay đổi.

Parameter Store vs Secrets Manager

Parameter Store: rẻ, không auto-rotate. Secrets Manager: có phí, auto-rotate tích hợp RDS/Aurora.

Config vs CloudTrail

Config = trạng thái cấu hình + compliance. CloudTrail = ai gọi API gì. Đừng nhầm trong câu hỏi audit.

RAM

Chia sẻ resource giữa account, không cần duplicate hạ tầng — hay đi cùng AWS Organizations.

DR Strategies

Backup&Restore → Pilot Light → Warm Standby → Multi-site Active/Active. Luôn chọn phương án rẻ nhất đáp ứng đủ RTO/RPO.

Nested Stack

Template con bắt buộc nằm trên S3 (TemplateURL), không dùng file:// local như stack gốc.

🎯 Pattern chuẩn thi

Khi đề cho RTO/RPO cụ thể → chọn chiến lược DR rẻ nhất đáp ứng đủ. Khi hỏi "tránh downtime khi update hạ tầng" → Change Set / Immutable deployment. Khi hỏi "audit trạng thái cấu hình" → Config, không phải CloudTrail.

🏭 Trạm mới thêm vào nhà máy nền

  • CloudFormation — bản vẽ + đội thi công dựng toàn nhà máy
  • Elastic Beanstalk — combo đóng gói ALB+ASG/EC2
  • Parameter Store / Secrets Manager — sổ tay cấu hình/bí mật cạnh KMS
  • AWS Config — nhân viên kiểm định cấu hình (khác GuardDuty)
  • AWS RAM — hợp đồng thuê chung hạ tầng giữa account
  • RPO/RTO/DR — bản kế hoạch dự phòng toàn nhà máy
